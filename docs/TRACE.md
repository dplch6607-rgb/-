# Ручная трассировка собственных алгоритмов

Трассировки сняты реальным прогоном логики из `workshop/algorithms.py` на маленьком примере
(остатки на складе: `[40, 10, 400, 5, 250, 3]`).

## 1. Сортировка слиянием: `merge_sort(items, key=on_hand)`

Идея: разделить список пополам, отсортировать половины рекурсивно, затем **слить** две
упорядоченные половины, каждый раз беря меньший из двух «передних» элементов.

```
split [40, 10, 400, 5, 250, 3] -> [40, 10, 400] | [5, 250, 3]
  split [40, 10, 400] -> [40] | [10, 400]
    split [40] -> базовый случай
    split [10, 400] -> [10] | [400]
      split [10] -> базовый случай
      split [400] -> базовый случай
    merge [10] + [400] -> [10, 400]
  merge [40] + [10, 400] -> [10, 40, 400]
  split [5, 250, 3] -> [5] | [250, 3]
    split [5] -> базовый случай
    split [250, 3] -> [250] | [3]
      split [250] -> базовый случай
      split [3] -> базовый случай
    merge [250] + [3] -> [3, 250]
  merge [5] + [3, 250] -> [3, 5, 250]
merge [10, 40, 400] + [3, 5, 250] -> [3, 5, 10, 40, 250, 400]
```

Последнее слияние по шагам (`i` — позиция в левом списке, `j` — в правом):

| Шаг | left[i] | right[j] | Сравнение | Берём | Результат |
|---|---|---|---|---|---|
| 1 | 10 | 3 | 10 ≤ 3? нет | 3 (справа) | `[3]` |
| 2 | 10 | 5 | 10 ≤ 5? нет | 5 (справа) | `[3, 5]` |
| 3 | 10 | 250 | 10 ≤ 250? да | 10 (слева) | `[3, 5, 10]` |
| 4 | 40 | 250 | 40 ≤ 250? да | 40 (слева) | `[3, 5, 10, 40]` |
| 5 | 400 | 250 | 400 ≤ 250? нет | 250 (справа) | `[3, 5, 10, 40, 250]` |
| 6 | 400 | — | правый список кончился | хвост слева | `[3, 5, 10, 40, 250, 400]` |

**Сложность.** Глубина рекурсии ≈ log₂ n (6 элементов → 3 уровня разделения), на каждом уровне
слияния суммарно просматривается n элементов ⇒ время **O(n log n)** всегда (лучший, средний и
худший случаи), память **O(n)** на временные списки.

**Устойчивость.** При равных ключах в слиянии берётся элемент из *левой* половины (`<=`), поэтому
порядок равных записей сохраняется. Это позволяет сортировать по двум полям: сначала по названию,
затем по категории — внутри категории порядок по названию сохранится.

## 2. Бинарный поиск: `binary_search_left(records, target)`

Предусловие: список **отсортирован** по тому же ключу. На каждом шаге отбрасывается половина диапазона
`[lo, hi)`; ищется первая позиция, где `ключ >= target`.

### Поиск 40 в `[3, 5, 10, 40, 250, 400]`

| Шаг | lo | hi | mid | a[mid] | a[mid] < 40? | Действие |
|---|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 40 | нет | `hi = mid = 3` |
| 2 | 0 | 3 | 1 | 5 | да | `lo = mid + 1 = 2` |
| 3 | 2 | 3 | 2 | 10 | да | `lo = mid + 1 = 3` |
| — | 3 | 3 | | | | `lo == hi` → стоп |

`lo = 3`, `a[3] == 40` ⇒ найдено, индекс **3**.

### Поиск 7 (нет в списке)

| Шаг | lo | hi | mid | a[mid] | a[mid] < 7? | Действие |
|---|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 40 | нет | `hi = 3` |
| 2 | 0 | 3 | 1 | 5 | да | `lo = 2` |
| 3 | 2 | 3 | 2 | 10 | нет | `hi = 2` |
| — | 2 | 2 | | | | `lo == hi` → стоп |

`lo = 2`, но `a[2] = 10 ≠ 7` ⇒ в `binary_search` результат **-1**, а `binary_search_left` отдаёт
точку вставки **2**.

**Сложность.** Диапазон делится пополам: ⌈log₂ n⌉ шагов ⇒ **O(log n)**, память O(1).

### Как это используется в проекте

*Поиск по началу названия.* Предметы один раз сортируются по `название.casefold()` (результат кэшируется
в `Inventory._name_view`). Все названия с общим началом идут подряд, поэтому находим точку вставки префикса
бинарным поиском и идём вперёд, пока название начинается с префикса: **O(log n + k)**, где k — число найденных.

*Поиск выдачи по номеру.* Номера выдач растут и выдачи не удаляются ⇒ журнал всегда отсортирован по
`loan_id`, бинарный поиск работает без дополнительной сортировки.
