## Что говорить

**Структура данных: `Inventory`.** Три коллекции под три задачи: `list` хранит порядок и даёт
материал для сортировки; `dict` «артикул → предмет» находит предмет за O(1) при каждой выдаче и
возврате (в списке пришлось бы перебирать O(n)); `set` хранит уникальные категории, повторы
отсекаются сами. Цена: при удалении список приходится сдвигать (O(n)), а индекс и множество — обновлять.

**Решение по архитектуре: композиция + фасад.** `Workshop` создаёт и владеет `Inventory`, журналом
выдач и очередью заявок; снаружи они не живут. Интерфейс (`ui.py`) и хранение (`storage.py`) знают
только про `Workshop`, а не про его внутренности. Наследование использовано один раз и только там,
где верно «является»: инструмент *является* предметом, расходник *является* предметом. `Loan` и
`LoanRequest` — данные, не предметы, поэтому они `dataclass` без наследования.

**Алгоритм: сортировка слиянием.** Делим пополам, сортируем рекурсивно, сливаем. O(n log n)
всегда, память O(n), **устойчивая**. Почему не пузырёк: O(n²). Почему не быстрая: худший случай O(n²)
и неустойчива. Трассировка — в `docs/TRACE.md`.

**Полиморфизм.** `Consumable` и `ReusableTool` отвечают на одни и те же вызовы по-разному: `take`
у обоих уменьшает остаток, `give_back` у инструмента возвращает единицы, а у расходника запрещён;
`needs_attention` у инструмента сигналит при «всё выдано», у расходника — при «ниже минимума».
`build_report` просто вызывает `item.needs_attention()` для любого предмета и не знает его тип.

**Очередь.** `deque`, потому что `popleft()` за O(1) (у `list.pop(0)` — O(n)). Очередь FIFO **по каждому
предмету**: пока ранняя заявка на предмет X не выполнена, поздние заявки на X тоже ждут (множество
`blocked`), иначе маленькие заявки обгоняли бы большие. Цена справедливости: поздняя маленькая заявка
может ждать, хотя запас на неё есть. Заявки на разные предметы друг друга не блокируют.

**Генератор.** Импорт CSV — цепочка генераторов: чтение → проверка → преобразование → создание.
В памяти всегда одна строка, а не весь файл. Плохая строка отклоняется отдельно: причина попадает в
`ImportResult` и в журнал, остальные строки импортируются.

**Устойчивость.** Ввод проверяется на границе (`ui.py`: повторный запрос), данные файла — на границе
(`storage.py`), а состояние объектов защищено `property` (количество не может быть отрицательным,
`available` не больше `total`). Ошибки предметной области — наследники `WorkshopError`; `except`
всегда указывает конкретный тип. JSON пишется во временный файл и переименовывается (`os.replace`),
поэтому сбой при записи не портит старое состояние.

## Типовые вопросы

1. **Почему бинарный поиск нельзя применять к любому списку?** Он отбрасывает половину диапазона, опираясь
   на упорядоченность. На неотсортированных данных ответ неверен. Поэтому в `Inventory` для него
   есть отсортированное представление, а журнал выдач по построению упорядочен по `loan_id`.
2. **Зачем бинарный поиск, если есть dict?** dict ищет только точное совпадение. Поиск «начинается с…»
   через dict невозможен; бинарный даёт O(log n + k) после одной сортировки.
3. **Что такое устойчивая сортировка и где она нужна?** Равные ключи сохраняют исходный порядок.
   Нужна для сортировки по нескольким полям подряд.
4. **Почему `Item` абстрактный?** Предмета «вообще» не бывает, всегда инструмент или расходник;
   абстрактные методы заставляют каждый подкласс реализовать полный интерфейс.
5. **Зачем `sku`, `name`, `category` без setter?** `Inventory` держит по ним индекс и кэш; прямое присваивание
   сломало бы их. Менять можно только через `Inventory.update()`, который сначала проверяет оба значения, потом применяет.
6. **Почему `LoanRequest` — `frozen`?** Заявка в очереди не должна меняться: поменялись бы условия ожидания.
7. **Почему своё исключение, а не `ValueError`?** Интерфейс ловит `WorkshopError` и показывает сообщение, но не
   скрывает настоящие баги (`TypeError`, `KeyError`). `ValidationError` при этом наследует и `ValueError`.
8. **Что будет при повреждённом `state.json`?** `load_state` бросает `StorageError`, `main.py` пишет понятное сообщение
   и завершается с кодом 1: молча продолжать с мусором нельзя.
9. **Как найти дефект, который вы исправили?** `git log`: коммит `test: воспроизведён дефект очереди…`
   (тест падает) и коммит `fix: очередь FIFO…` (проходит). Описание в конце `docs/TEST_CASES.md`.
10. **Сложность `remove`?** O(n): `list.remove` + пересборка множества категорий. Это осознанная цена за O(1)-поиск и
    O(1)-добавление при редком удалении.

## Типовые правки «по просьбе преподавателя» (где менять)

| Просьба | Где | Что сделать |
|---|---|---|
| Сортировка по двум полям (категория, затем название) | `ui.py` / `Inventory.sorted_by` | Сначала `merge_sort` по `name`, потом по `category` — устойчивость сохранит порядок внутри категории |
| Считать «заканчивается» при остатке **не больше** минимума | `Consumable.needs_attention` | заменить `<` на `<=` |
| Новый режим поиска «оканчивается на…» | `Inventory.search` + `SEARCH_MODES` в `ui.py` | ещё одна ветка с `linear_find_all` |
| Ограничить число инструментов на руках у одного человека | `Workshop.issue` / `request_item` | посчитать `sum(l.quantity for l in iter_active_loans() if l.borrower == …)` и бросить `ValidationError` |
| Добавить срок возврата | `Loan` (+`due_on`), `to_dict/from_dict`, `build_report` | поле `date`, в отчёт — список просроченных |
| Новый тип предмета (например, «Комплект») | `models.py` | подкласс `Item`, запись в `_ITEM_KINDS` — остальной код не меняется (полиморфизм) |
